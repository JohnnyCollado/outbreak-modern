## Rationale
- Field presentation first: it touches every screen's frame, so measuring ACCESS/CAPCOM faults before it would mix two faults in one number (developer order, GENERATION_PLAN 1.3 scope).
- The trace (T2) before the logo fixes: the decomp cannot give the logos' TEX0/CLUT/ALPHA/TEXA/XYOFFSET (R1.3-001), and PCSX2 needs a proceed per launch. What it does: logs per-draw GS state in two capture windows. What exists: frame dump and the input script's `watch` show pixels and guest RAM, not GS registers (EeScheduler.cpp:1897-1906 masks `watch` to RDRAM, R1.3-004). The delta: the register values ACCESS and CAPCOM are drawn with. It is a temp hunk, not a patch or a tool (house rules §3).
- ACCESS before CAPCOM (scope order); one task per fault so each gate run shows one screen's share falling.
- `effort: high` on T3 only: the ACCESS share has several candidate causes in the shared GS path (R1.3-002), and the judgment no test arbitrates is which of them is the real fault; a fix that greens ACCESS by fitting PCSX2's frame while breaking the GS semantics it rests on would pass the gate. T4's CAPCOM fault is geometric and the gate plus a unit test arbitrate it.
- T5 is separate from the fault tasks: the milestone evidence comes from a forced recompile and two runs of one build (house rules §5), and it writes the 1.3 baseline the next phase starts from.

Then the task returns `blocked` with evidence and a recommendation; the milestone or scope moves only through the developer.

- The stale gate (346 s) exceeds a tool call; a background run can be killed by the low-memory guard in its report phase: re-run in the foreground on the fresh stamp.
