## Struggles

### 1. Folder test expected the on-disk case of a file name

- **Seen:** `game source: an extracted folder boots its SYSTEM.CNF's BOOT2 (any case)` failed (513/514).
- **Found by:** the assertion message (`boot ELF matched ignoring case`).
- **Cause:** NTFS is case-insensitive: `exists(folder / "SLUS_123.45")` is true for the file `slus_123.45`, so the
  lookup returns the name as asked, not as stored. The code is right on both; the test compared names.
- **Fix:** the test checks `std::filesystem::equivalent` with the stored file.
- **Evidence:** `C:\ob\logs\ob-test-ps2x.log` (513/514, then 514/514).
- **Take-away:** on Windows, compare files, not spellings.

### 3. PCSX2 GS on arm64: three compile errors

- **Seen:** `ob_pcsx2_gs` for Android: `dxgi1_5.h` not found (`stubs/gs_stubs.cpp`), `shm_open`/`shm_unlink`
  undeclared (`GS/GS.cpp:1044-1047`, and `common/Linux/LnxHostSys.cpp`), and in the runner tree `DWORD`,
  `GetCurrentThread(Id)` undeclared (`adapter/pcsx2_side.cpp`).
- **Cause:** the D3D stubs were unconditional; bionic has no POSIX shared memory; the GS thread code named Win32
  types.
- **Fix:** D3D stubs under `_WIN32`; `stubs/android/ob_android_compat.h` force-included into the GS library declares

  only from API 30) plus the non-desktop functions of `LnxMisc.cpp` (not built: X11, D-Bus); `DWORD`/`gettid` and
  `pthread_setname_np` on Android in `pcsx2_side.cpp`. No PCSX2 source edit for these.
- **Evidence:** `C:\ob\logs\ob-android-gs-build.log` (first run 3 errors, second run clean, 33 s).
- **Take-away:** PCSX2's Linux code path is close to Android; X11/D-Bus and shm are the only real gaps for the GS.

### 5. A one-file change cost a 4-minute link

- **Seen:** after patch 0044 (one runtime source), `android build`: 4 steps, 241 s; `.ninja_log`: the
  `libps2EntryRunner.so` link 236.7 s (352.8 s in the first build).
- **Found by:** `.ninja_log` step times; the unstripped `.so` is 604 MB (72 MB stripped).
- **Cause:** the NDK toolchain puts `-g` in every compile (560 `-g` in `build.ninja`); lld spends the time on ~530 MB
  of debug sections it then gets stripped from the APK anyway. Windows builds have no debug info by default.
- **Fix, first try:** `-g0` in the release flags (after the toolchain's `-g`, so it wins): full build 318 s, but the
  link after a one-file change still 139.8 s. The link command had `-flto=thin`: PS2Recomp's `ReleaseMode.cmake`
  turns IPO on for the `Release` config, so lld ran ThinLTO code generation for the whole game on every link.
  Windows never sees it: `ob.sh recompile` builds `RelWithDebInfo` with its own flags.
- **Fix:** the Android tree is `RelWithDebInfo` with `CMAKE_C/CXX_FLAGS_RELWITHDEBINFO="-O3 -DNDEBUG -g0"`, as Windows.
  Full build 249 s (542 steps, 329 game units); after touching one runtime file: 4 s, link 0.5 s; `.so` 70 MB
  (65 MB stripped); APK 22.0 MB. shaderc keeps `Release` (built once).
- **Evidence:** `C:\ob\logs\ob-android-build.log`, `C:\ob\android-r\.ninja_log`.
- **Take-away:** check the link step, not only compile counts, for "incremental"; and read which config a
  third-party CMake turns LTO on for.

### 6. VU1 on arm64: software quad floats, and fused multiply-adds Windows never does (patch 0045)

- **Seen:** the developer reports J's Bar "very slow" on the Odin. VU1 there is PS2Recomp's interpreter.
- **Found by:** NDK clang `-S` of the VU files with the Android flags: `ps2_vu1_core.cpp` had 87 calls to the
  soft-float quad routines (`__addtf3`, `__multf3`, `__extendsftf2`, compares); `ps2_vu1_upper.cpp` 67 and
  `ps2_vu1_lower.cpp` 34 `fmadd`/`fmsub`. x86 indicator (MinGW `__float128`, libgcc soft-fp, not the Odin): one
  lane's flag check 89 ns vs 2.7 ns in double.
- **Cause:** (a) the FMAC flag/clamp check computes the unrounded result in `long double`: MSVC's is double, the
  NDK's is IEEE quad in software. Its only job is the Z/S/U/O flags and the clamp (the stored value is the float
  result). Double is exact for a VU float product; a sum rounds once toward zero, keeping sign and zero; the
  only difference from quad is a sum within one double step above FLT_MAX (FLT_MAX + 2^70: quad says overflow,
  Windows did not). (b) Clang's default contraction fused `acc + a*b` (one rounding, Windows and microVU: two),
  so Android VU1 results would differ in the last bits.
- **Fix:** double in the check; `#pragma STDC FP_CONTRACT OFF` (MSVC `fp_contract(off)`, GCC `optimize`) in
  `ps2_vu1_detail.h`. Plus per-cycle savings with unchanged results (commit early-out and per-queue valid masks,
  lazy decode cache, XGKICK buffer out of the cleared struct, inline `normalizeOperand`). After: 0 quad calls and
  0 fused ops in the Android objects; vucompare same 100/120 replay-exact set (`C:\ob\logs\vucompare-0045d.log`);
  Windows 181.7 -> 109.9 ns per VU1 cycle (`vucompare-0044-base.log`); ps2x 519/519; gate 3/3 (pcsx2-sw);
  `PS2X_GS=pcsx2-sw PS2X_VU1=interp` hidden `gate/jsbar.script` (play.script's steps, stops at J's Bar on room 1 /
  mode 2): J's Bar scene renders (`C:\ob\frames-jsbar-interp-0045`). Android incremental build 25 s (50 steps, 0
  game units), package 5 s, `android verify` ok.
- **Fail without:** MSVC cannot show it (its `long double` is double). A GCC build of 0044 (x87 80-bit
  `long double`, `C:\ob\g` + scratch harness) reports MAC `c000` on the FLT_MAX + 2^70 case (Windows `4000`); its
  upper file with `-mfma` gives MADD `0x3A000400` (Windows `0x3A000000`). 0045 under GCC with `-mfma`: both match.
- **Take-away:** a type that is "the same" on MSVC (`long double`) or a default that MSVC never applies
  (contraction) changes the arm64 build's speed and results; read the arm64 assembly of hot numeric files.

### 7. ARMSX2's ARM64 microVU as libob_a64vu.so: small surprises on the way to a clean link

- **Seen:** (a) first configure of `native/pcsx2_vu/a64` stopped at its own guard "expected 11 vuaot/*.cpp,

  (c) the first link left 102 external symbols, two more than the study's list (`SPU2Options()`, `DEV9Options()`).
- **Found by:** (a) `ls C:\ob\armsx2\pcsx2\arm64\vuaot\*.cpp` (10 files); the study's "11 vuaot TUs" counted

  `config_defaults_a64.cpp` owns `EmuConfig`, so every option struct's constructor must exist in the `.so`.
- **Fix:** (a) guard expects 10; (b) the compare tool uses `InitOwned` + `OwnedData()/OwnedCode()` on both

- **Then (runner hookup, patch 0048):** a NEEDED `libob_a64vu.so` would make a load failure an app that cannot
  start, so the runner now loads it: `adapter/hook.cpp` with `OB_PCSX2_VU_DLOPEN` (Android) dlopens it, dlsyms

### 8. Custom GPU driver on Android: libadrenotools, a PCSX2 hand-off hook, `gpu_driver` (patch 0046)

- **Seen:** the developer approved letting players pick the system Vulkan driver or their own (Turnip on Adreno).
  PCSX2 opens `libvulkan.so` itself inside `Vulkan::LoadVulkanLibrary` (`VKLoader.cpp:46-88`), from a file-static
  `DynamicLibrary`, and re-opens it for every device it creates and for adapter enumeration
  (`GSDeviceVK.cpp:400-412`, `:2656`). outbreak.ini rejected any unknown key as a bad line (patch 0043).
- **Found by:** reading libadrenotools at `8fae8ce` (`include/adrenotools/driver.h`, `src/driver.cpp`,
  `src/hook/CMakeLists.txt`, `tools/ADPKG.md`): the hooks are two shared libraries that must be in
  `nativeLibraryDir` (libraries extracted), the driver must be in internal storage, the driver directory is
  concatenated with the library name (needs the trailing `/`). ARMSX2 (GPL-3.0) calls it inside PCSX2's loader
  and lets `Close()` dlclose the handle on every unload.
- **Cause:** design work, no fault.
- **Fix:** PCSX2 patch `upstream/pcsx2/0002` (`SetPreloadedVulkanLibrary`: entry points by `dlsym` from a
  host-owned handle, never closed by PCSX2); `native/pcsx2_gs/adapter/gpu_driver.{h,cpp}` (pure: setting,
  `meta.json`, library pick, one fall-back decision, log lines, sync stamps) and `gpu_driver_android.{h,cpp}`
  (copy external -> internal, Adreno check by `/dev/kgsl-3d0`, `adrenotools_open_libvulkan`, probe instance +
  device, hand-off; fall back with one line on any failure, a second `GSopen` with the system driver if PCSX2
  still fails); PS2Recomp patch 0046 (`gpu_driver` key, desktop note); `android.sh` clones the pin, builds
  libadrenotools from source in the Android tree, packages and symchecks the hooks. After: Android incremental
  build 6 s (21 steps, 0 game units, libadrenotools included), APK 22.1 MB, `android verify` ok (4 libraries);
  `ob.sh test` ps2x 521/521, pcsx2_gs 68/68 (ob_gpu_driver_tests 52/52); depcheck ok; gate 3/3 gated green with 0046 and 0047 (pcsx2-sw, wall 97 s after a 46 s recompile).
- **Fail without:** 0046's ps2x case does not compile without the patch (no `Settings::gpuDriver`, no
  `gpuDriverNote`); without 0002 the adapter has no way to give PCSX2 the handle (link error on Android).
- **Take-away:** keep the vendor library out of PCSX2: one small hand-off hook in PCSX2, the policy in our adapter
  where it is host-testable.
- Small slip: `git -C C:\ob\pcsx2 format-patch -o upstream\pcsx2` resolved the relative path against `C:\ob\pcsx2`;
  the patch was moved to the repo and the stray folder removed. Use an absolute `-o`.
- Small slip: a Python heredoc with `C:\\ob\\adrenotools` wrote a BEL character (`\a`) into pins.md; fixed by
  character code (the `heredoc-escaping-trap` note applies to Markdown too).

### 11. Black light glows on the Odin: Qualcomm's driver and PCSX2's destination read (investigation)

- **Seen:** J's Bar on the Odin (`C:\ob\odin-shot2.png`; side by side with Windows `C:\ob\logs\odin-vs-windows-lights.png`):
  large black disks where the lamp glows are, covering the windows; the Windows runner with the same PCSX2 Vulkan
  renderer draws them. The black in-game menu background was not captured yet (the black frame taken was the scene's
  event transition, `odin-shot3.png`).
- **Found by:** reading PCSX2 2.9.134 `GSDeviceVK.cpp` `CheckFeatures` (:2790-2896): `framebuffer_fetch` = the driver
  offers VK_EXT_rasterization_order_attachment_access and `DisableFramebufferFetch` is off; `texture_barrier` =
  `OverrideTextureBarriers != 0` (default -1); no vendor case anywhere in its Vulkan renderer (only DX12 has an Adreno
  barrier note, `GSDevice12.cpp:1542-1594`). ARMSX2 `90126bd` `GSDeviceVK.cpp` (read from the pinned clone):
  "The Qualcomm driver on Adreno 8xx returns stale rasterization-order reads above Basic blending" (a hard gate on
  fetch, :4066-4067), a `UseRenderTargetCopyForFeedback` workaround that turns texture barriers off on Adreno so the
  destination is read from a copy of the target (:4030-4047, :4136-4146), and "Qualcomm's Adreno driver selects the
  wrong provoking vertex" (:1194-1197).
- **Cause (likely, unverified until the fix runs):** the glows (and probably the menu's frame copy) blend with the
  colour already drawn; on Qualcomm's driver PCSX2's in-pass read of it returns stale or zero values, so they come out
  black. Windows never takes that road (no Qualcomm driver).
- **Mali (developer's request):** unmodified PCSX2 requires push descriptors (`GSDeviceVK.cpp:818-829`); ARMSX2
  notes that some Mali drivers lack them (Mali-G52) and Arm's driver crashes in `vkCmdPushDescriptorSetKHR` even where
  offered (:184-187, :1186-1190), plus Mali feedback-loop device loss (r44p1), broken destination reads on some
  MediaTek Mali, and a depth/stencil load-op corruption (:1160-1166, :4049-4053, :1491-1497). No Mali device here.

### 14. Full-resolution window on Android, and the picture re-tested

- **Cause (verified):** raylib's `InitGraphicsDevice` sets the window's buffers to its render size (`rcore_android.c`
  :906-908: `ANativeWindow_setBuffersGeometry(render width/height)`; 796x448 for the runner's 640x448 screen on a
  1920x1080 display), and the adapter handed that window to PCSX2 at its current size (`pcsx2_side.cpp`
  `ob_gs_attach_window`).
- **Fix:** `ob_gs_attach_window` (Android) calls `ANativeWindow_setBuffersGeometry(win, 0, 0, 0)` after it releases
  raylib's EGL surface: the window's own size, so PCSX2 presents at the display's resolution. Logcat:
  `attach android window 1920x1080`, `open ... surface=1920x1080`. raylib still believes 640x448 (it draws nothing
  after the hand-over; input is the gamepad).
- **Checks:** PC suites green (ps2x 533/533, pcsx2_gs 84/84, iop 5/5, gs_cache 45/45, ob_diag 23/23, pcsx2_vu 3/3);
  Android build 4 s, symcheck ok. Odin, same spot (Kevin at the bar), crops `C:\ob\logs\kevin-fullres-compare.png`:
  run 1 full resolution, defaults (upscale 1, nearest present): sharper but blocky (PCSX2's nearest 2.41x stretch
  instead of Android's smoothing), 60.0 fps; run 2 + `upscale = 3`: hair strands, face and the room far sharper, the
  black face streaks resolve as hair strands, 59.99 fps mean (min 59.0); run 3 + smooth scaling (throwaway build):
  slightly softer than run 2, same speed. Logs `C:\ob\logs\odin-fullres-run{1,2,3}.log`.
- **Defaults:** unchanged (upscale 1, nearest present); the developer decides.
