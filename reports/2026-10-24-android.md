# Game data from the disc image, and the Android A1 build

- **Date:** 2026-10-24
- **Who:** Claude Code session (agent), for the developer's approved Android Stage A1 and data model
- **Goal:** (1) the runner reads the game from an ISO 9660 image (or an extracted folder) with a settings file
  (`game`, `textures`, `mods`); (2) an arm64 APK of the runner with PCSX2's Vulkan GS, built without Gradle, ready
  for the developer to install on the AYN Odin 3 Max.
- **Outcome:** patches 0043/0044 in; gate 3/3 from the ISO; `outbreak-modern.apk` (22.0 MB, v3-signed, all symbols
  resolve offline). Not run on a device yet (needs the developer's "proceed"; commands in `docs/ops/android.md`).
  Follow-up patch 0045 (entry 6): VU1 without software quad floats or fused multiply-adds on arm64; APK rebuilt.
- **Versions:** PS2Recomp `eb8688b` + patches 0001-0045 (`C:\ob\up`), PCSX2 v2.9.134 `a81f1aa` + `upstream/pcsx2/0001`,
  MSVC 19.44, NDK 27.0.12077973, build-tools 35.0.0, CMake 3.30, Windows 11.

## Summary

Part 1 (patch 0043) went in without a struggle worth the name: one test assumption about case on Windows, and a
fail-without check that first ran against an unreverted copy. The gate is 3/3 (max 0) booted from the ISO and from
`game_files`, and `gate/play.script` from the ISO reaches J's Bar. Part 2: PCSX2's GS compiled for arm64 with three
fixes (a D3D shim, POSIX shared memory, Win32 thread calls), shaderc for arm64 from the pinned sources, and one
missing dependency fetch (sse2neon) for the runner tree. See the entries for the Android build numbers.

## Struggles

### 1. Folder test expected the on-disk case of a file name

- **Seen:** `game source: an extracted folder boots its SYSTEM.CNF's BOOT2 (any case)` failed (513/514).
- **Found by:** the assertion message (`boot ELF matched ignoring case`).
- **Cause:** NTFS is case-insensitive: `exists(folder / "SLUS_123.45")` is true for the file `slus_123.45`, so the
  lookup returns the name as asked, not as stored. The code is right on both; the test compared names.
- **Fix:** the test checks `std::filesystem::equivalent` with the stored file.
- **Evidence:** `C:\ob\logs\ob-test-ps2x.log` (513/514, then 514/514).
- **Take-away:** on Windows, compare files, not spellings.

### 2. Fail-without check ran against the patched copy

- **Seen:** with the EE/VFS changes "reverted" the suite was still 514/514.
- **Found by:** grepping `C:\ob\src` for `IsoImage` (still there) and ninja's "no work to do".
- **Cause:** the shell command that copied the `HEAD` versions failed to parse (a stray quote in a `source <(...)`
  helper), so nothing was copied.
- **Fix:** copy the two files with plain `git show HEAD:<file> >`, rebuild: 512/514, the two image cases fail
  (`C:\ob\logs\failwithout-run.log`), then restore and `cmp` against `C:\ob\up`.
- **Take-away:** check the revert landed (grep or `cmp`) before trusting a fail-without run.

### 3. PCSX2 GS on arm64: three compile errors

- **Seen:** `ob_pcsx2_gs` for Android: `dxgi1_5.h` not found (`stubs/gs_stubs.cpp`), `shm_open`/`shm_unlink`
  undeclared (`GS/GS.cpp:1044-1047`, and `common/Linux/LnxHostSys.cpp`), and in the runner tree `DWORD`,
  `GetCurrentThread(Id)` undeclared (`adapter/pcsx2_side.cpp`).
- **Cause:** the D3D stubs were unconditional; bionic has no POSIX shared memory; the GS thread code named Win32
  types.
- **Fix:** D3D stubs under `_WIN32`; `stubs/android/ob_android_compat.h` force-included into the GS library declares
  `shm_open`/`shm_unlink`, `stubs/android/android_common.cpp` implements them with `memfd_create` (syscall: libc has it
  only from API 30) plus the non-desktop functions of `LnxMisc.cpp` (not built: X11, D-Bus); `DWORD`/`gettid` and
  `pthread_setname_np` on Android in `pcsx2_side.cpp`. No PCSX2 source edit for these.
- **Evidence:** `C:\ob\logs\ob-android-gs-build.log` (first run 3 errors, second run clean, 33 s).
- **Take-away:** PCSX2's Linux code path is close to Android; X11/D-Bus and shm are the only real gaps for the GS.

### 4. Runner tree: sse2neon not populated

- **Seen:** every runtime and game unit: `fatal error: 'sse2neon.h' file not found` (43 FAILED, PCH first).
- **Found by:** the configure log: `FETCHCONTENT_FULLY_DISCONNECTED is set to true, which requires the source
  directory for dependency sse2neon to already be populated`.
- **Cause:** `tools/ob/android.sh` configured fully disconnected (to keep raylib offline); PS2Recomp's top
  `CMakeLists.txt:43-56` fetches sse2neon for ARM targets.
- **Fix:** drop `FULLY_DISCONNECTED`, keep `FETCHCONTENT_SOURCE_DIR_RAYLIB` (raylib stays the Windows tree's
  copy); sse2neon fetched once from GitHub (DLTcollab/sse2neon, tag `v1.9.1` = `92f6de1`, PS2Recomp's own pin).
- **Evidence:** `C:\ob\logs\ob-android-configure.log`, `C:\ob\android-fetch\sse2neon-src`.
- **Take-away:** an ARM configure of PS2Recomp needs that one fetch; it is cached after.

### 5. A one-file change cost a 4-minute link

- **Seen:** after patch 0044 (one runtime source), `android build`: 4 steps, 241 s; `.ninja_log`: the
  `libps2EntryRunner.so` link 236.7 s (352.8 s in the first build).
- **Found by:** `.ninja_log` step times; the unstripped `.so` is 604 MB (72 MB stripped).
- **Cause:** the NDK toolchain puts `-g` in every compile (560 `-g` in `build.ninja`); lld spends the time on ~530 MB
  of debug sections it then gets stripped from the APK anyway. Windows builds have no debug info by default.
- **Fix, first try:** `-g0` in the release flags (after the toolchain's `-g`, so it wins): full build 318 s, but the
  link after a one-file change still 139.8 s. The link command had `-flto=thin`: PS2Recomp's `ReleaseMode.cmake`
  turns IPO on for the `Release` config, so lld ran ThinLTO code generation for the whole game on every link.
  Windows never sees it: `ob.sh recompile` builds `RelWithDebInfo` with its own flags.
- **Fix:** the Android tree is `RelWithDebInfo` with `CMAKE_C/CXX_FLAGS_RELWITHDEBINFO="-O3 -DNDEBUG -g0"`, as Windows.
  Full build 249 s (542 steps, 329 game units); after touching one runtime file: 4 s, link 0.5 s; `.so` 70 MB
  (65 MB stripped); APK 22.0 MB. shaderc keeps `Release` (built once).
- **Evidence:** `C:\ob\logs\ob-android-build.log`, `C:\ob\android-r\.ninja_log`.
- **Take-away:** check the link step, not only compile counts, for "incremental"; and read which config a
  third-party CMake turns LTO on for.

### 6. VU1 on arm64: software quad floats, and fused multiply-adds Windows never does (patch 0045)

- **Seen:** the developer reports J's Bar "very slow" on the Odin. VU1 there is PS2Recomp's interpreter.
- **Found by:** NDK clang `-S` of the VU files with the Android flags: `ps2_vu1_core.cpp` had 87 calls to the
  soft-float quad routines (`__addtf3`, `__multf3`, `__extendsftf2`, compares); `ps2_vu1_upper.cpp` 67 and
  `ps2_vu1_lower.cpp` 34 `fmadd`/`fmsub`. x86 indicator (MinGW `__float128`, libgcc soft-fp, not the Odin): one
  lane's flag check 89 ns vs 2.7 ns in double.
- **Cause:** (a) the FMAC flag/clamp check computes the unrounded result in `long double`: MSVC's is double, the
  NDK's is IEEE quad in software. Its only job is the Z/S/U/O flags and the clamp (the stored value is the float
  result). Double is exact for a VU float product; a sum rounds once toward zero, keeping sign and zero; the
  only difference from quad is a sum within one double step above FLT_MAX (FLT_MAX + 2^70: quad says overflow,
  Windows did not). (b) Clang's default contraction fused `acc + a*b` (one rounding, Windows and microVU: two),
  so Android VU1 results would differ in the last bits.
- **Fix:** double in the check; `#pragma STDC FP_CONTRACT OFF` (MSVC `fp_contract(off)`, GCC `optimize`) in
  `ps2_vu1_detail.h`. Plus per-cycle savings with unchanged results (commit early-out and per-queue valid masks,
  lazy decode cache, XGKICK buffer out of the cleared struct, inline `normalizeOperand`). After: 0 quad calls and
  0 fused ops in the Android objects; vucompare same 100/120 replay-exact set (`C:\ob\logs\vucompare-0045d.log`);
  Windows 181.7 -> 109.9 ns per VU1 cycle (`vucompare-0044-base.log`); ps2x 519/519; gate 3/3 (pcsx2-sw);
  `PS2X_GS=pcsx2-sw PS2X_VU1=interp` hidden `gate/jsbar.script` (play.script's steps, stops at J's Bar on room 1 /
  mode 2): J's Bar scene renders (`C:\ob\frames-jsbar-interp-0045`). Android incremental build 25 s (50 steps, 0
  game units), package 5 s, `android verify` ok.
- **Fail without:** MSVC cannot show it (its `long double` is double). A GCC build of 0044 (x87 80-bit
  `long double`, `C:\ob\g` + scratch harness) reports MAC `c000` on the FLT_MAX + 2^70 case (Windows `4000`); its
  upper file with `-mfma` gives MADD `0x3A000400` (Windows `0x3A000000`). 0045 under GCC with `-mfma`: both match.
- **Take-away:** a type that is "the same" on MSVC (`long double`) or a default that MSVC never applies
  (contraction) changes the arm64 build's speed and results; read the arm64 assembly of hot numeric files.
