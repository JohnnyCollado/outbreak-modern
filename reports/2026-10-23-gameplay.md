# Gameplay bring-up: past character select (2026-10-23)

Goal: get the scripted boot from character select into a scenario's first room with the player moving.
Script: `gate/play.script` (reuses `gate/boot.script` up to character select).

## 1. Difficulty screen timed out back to the title

- **Seen:** the first run (`play1`) ended with a script timeout (exit 3); the game was back at the title at tick 20599.
- **Found by:** watches on SelectWork state (`*0x003065FC+4`).
- **Cause:** the script waited for select state 10, which lasts only 2 ticks (9 -> 10 -> 11 at ticks 2617/2619).
  State 11 is the Difficulty screen; it sat until the 9000-tick idle timer (`title.c:1314`) returned to the title.
  The comments in `title.c:3517` and `gate/boot.script` ("10/11 = Difficulty") are imprecise: 11 is Difficulty.
- **Fix:** `gate/play.script` waits on state 11.
- **Take-away:** wait on the state a screen sits in, not a transition state; check short-lived states with a watch.

## 2. Black screen after Difficulty: GAME overlay never recompiled

- **Seen:** after confirming NORMAL, the screen fades to black and stays black (`C:\ob\frames-play2\gameload-0`,
  `load5s-0`, `load30s-1` identical). No loading screen.
- **Found by:** watches on task slot 4 (`0x002F8654`) and the overlay slots (`0x00239F30`, `0x00239F34`), and the
  runtime's branch log.
- **Cause:** at tick 2843 `func_001B6880` (`en\main\text.s:222301-222329`) installs a new main task in slot 4
  (0x540080 -> 0x5CD580) and requests overlays 2 (GAME) and 8 (SINGLE). Both load at ticks 2847-2848
  (`\PROG\GAME.BIN;1` size 0x1ce280 at 0x540000, replacing DEMO; `\PROG\SINGLE.BIN;1` size 0x1b780 at 0x820000).
  The task runner at 0x1b652c then calls `func_005CD580`, which exists only in GAME
  (`C:\ob\splat\SLPM_654.28\en\game\text.s:163563`): `boot-play2.err:60`
  `[guest-branch:missing-target] kind=IndirectCall op=JALR source=0x1b652c target=0x5cd580`. Policy 1 logs it
  and unwinds the thread (`ps2_runtime.h:97,307`). `tools/ob.sh` recompiled only `demo submain netdnas`.
- **Fix:** `tools/ob.sh` overlay loop now also recompiles `game single` (the guest-module registry is generic:
  each module is fingerprinted by 64 bytes at its load address, so GAME and DEMO can share 0x540000,
  `ps2_runtime.cpp:1195-1226`). Result: see the next entry.
- **Frame time:** the synchronous load of the two overlays costs 39-43 ms per tick for 3 ticks (`C:\ob\logs\play2.csv`).
- **Overlay ids** (name table `D_002136C0`, `en\main\data\vu_data.data.s:90138`): 0 SUBMAIN, 1 DEMO, 2 GAME,
  3 NETWK, 4 NETDNAS, 5 NETHTTP, 6 EDITOR, 7 NETAQ, 8 SINGLE.

## 3. NOW LOADING crawls at ~1.5 vsync/s: VU1 interpreter throughput

- **Seen:** `play4`/`play5` reach "...NOW LOADING" (`C:\ob\frames-play5\load30s-1.png`), then 823 vsyncs take 337 s,
  busy == wall (`C:\ob\logs\play5.csv`). Two regimes: ticks 4160-4927 at 25-29 ms/frame, then from tick 4928
  600-675 ms/frame.
- **Found by:** patch 0030 (`PS2X_PC_SAMPLE`, `C:\ob\logs\play5-pc.csv`, 186k samples after tick 4608, ~550 Hz),
  `tools/ob/pc_profile.py`; then a throw-away probe in `VU1Interpreter::run` (`boot-vu1probe.err`, not a patch,
  `C:\ob\src` restored and cmp-equal to `C:\ob\up`).
- **Cause (verified):** from tick 4928, 93% of samples have the vu1 flag set, 94% at pc 0x18d01c in `func_0018CF10`
  (return of its `sceDmaSend`: a double-buffered display-list kick, `en\main\text.s:172723`). The VIF1 DMA runs
  synchronously and its MSCALs run the VU1 interpreter. Probe: per 2 s of wall time, ~3,300 MSCALs, ~10M VU1 cycles,
  1.8 s inside `run`, 0 budget (65536-cycle) hits. So the microprograms end normally (no runaway); the interpreter
  manages ~5.6M VU1 cycles/s, against ~147 MHz on hardware (~26x slower). Start pcs 0x528/0x640/0xb80/0x128/0x0/0x58
  make up ~80% of calls.
- **Secondary (verified):** in ticks 4160-4927, 73% of samples have the iop flag set while the pc sits in guest
  loops (chunk-table walkers `func_001A3250`/`func_001A31F0`, ADX read poll `func_001A9270`/`ADXF_GetStat`).
  Every backward-branch checkpoint calls `accountCycles(32)` -> `IopEmulator::runEeCycles` -> `runCycles`
  (`ps2xIOP/src/emulator/iop_emulator.cpp:564`: thread-map scans, timer service, a timeslice for 4 IOP cycles).
  Before the GAME load the same loops are 77-88% iop too, so the cost is per call, not load-specific.
  Unverified: which part of `runCycles` dominates.
- **Unverified:** whether ~3M VU1 cycles per vsync is the real workload (more than the hardware's ~2.5M per
  1/60 s, so the game may draw at 30 Hz here, or the interpreter's stall model over-counts).
- **Fix (proposed, not done; needs the partner's OK):** (1) VU1 speed: first profile `VU1Interpreter::run` on a
  captured microprogram (per-pair pipeline bookkeeping: VF/ACC save-restore memcpys, `queueVfWrite`,
  `calculatePairReadyCycle`), then a VU1 microprogram recompiler cached by code hash (the few start pcs above).
  Tuning alone probably will not close a 26x gap (guess). (2) IOP: batch `advanceIopEeCycles` (for example every
  2048 EE cycles or at the next IOP deadline) instead of every 32-cycle checkpoint.
- **Evidence:** `C:\ob\logs\play5-pc.csv`, `play5.csv`, `boot-vu1probe.err`, `vu1probe.csv`; phase split:
  ticks < 2816: vu1 0%, iop 10.2%, gs 1.7%, gsvsync 24.0% (88% outside guest code, idle);
  ticks >= 4608: vu1 90.8%, iop 3.4%, gs 0.5%, gsvsync 3.9%.
- **Take-away:** the busy == wall frames were VU1 microcode, not guest code. Sample before guessing, and split the
  run by phase: the first 300 loading ticks looked IOP-bound, the rest is VU1-bound.

## 4. VU1 capture (patch 0031): the duplicate-input check never matched

- **Seen:** the new test ran the same MSCAL program twice and expected one capture file; it got two (492/493).
- **Found by:** the test itself ("one capture file (the duplicate run is not written)").
- **Cause:** the input hash covered the whole VU1 state record, including the cycle counter (always different) and the
  pc/branch/stop/TOP/ITOP fields that `VU1Interpreter::execute` overwrites anyway.
- **Fix:** hash the state with the cycle counter zeroed and, for MSCAL, those overwritten fields zeroed
  (`ps2_vu1_capture.cpp`, `Recorder::begin`). Test 493/493; with the runtime hook removed it fails (no file, no
  summary). One unrelated flake in that fail-without run: "PS2X_FRAME_TIME counts the scheduler's idle wait" failed
  once under build load (vsyncs spanned < 10 ms), passed in the runs before and after.
- **Evidence:** `C:\ob\logs\ob-test-ps2x.log`; boot `vucap` (420 s, `play.script`): 495,616 VU1 runs, 120 files,
  6.2 MB, 30 keys over 8 distinct micro-memory images, 0 budget hits (`C:\ob\vu1-captures\summary.txt`).
- **Take-away:** the hot "start pcs" of entry 3 (0x528, 0x640, 0xb80, 0x128) are MSCNT continuations, not MSCAL
  starts: the game MSCALs at 0x0 and continues each next stage with MSCNT. Any VU1 backend must handle MSCNT
  as "resume at the pc after the last E bit".

## 5. microVU in a static library: link and build snags

- **Seen:** `pcsx2_side.cpp` failed to compile (`std::max` "illegal token"); the first link of the compare tool had
  49 unresolved symbols; a Python heredoc turned `\n` inside a C string into a real newline in `compare/main.cpp`.
- **Found by:** the build log `C:\ob\logs\ob-vu-build.log`.
- **Cause:** `<windows.h>` min/max macros; the unresolved list was the EE-recompiler/iCore/vtlb/VU0 glue the study
  predicted (~55, actual 49, none from PS2Recomp's side); the heredoc escaping trap (memory note).
- **Fix:** `NOMINMAX`; `native/pcsx2_vu/src/link_stubs.cpp` (49 stubs: data zeroed, functions abort with their name,
  `hwIntcIrq` no-op); the C++ edit redone with the Edit tool. The macro seam held: no PCSX2 source edit.
- **Evidence:** first clean build 54 s (includes this build dir's own `ob_pcsx2_gs`, 104 steps); `ob_mvu_jit.cpp`
  (all of microVU) 7.3 s; incremental tool rebuild 5-8 s. `tools/ob.sh depcheck`, named in the brief and
  `gate/baseline-1.3.md:82`, does not exist in `tools/ob.sh`; checked by hand instead: after patch 0031 the
  runner rebuilt 3 runtime objects and 0 game units in 23 s (`C:\ob\logs\ob-runner-build.log`).
- **Take-away:** a wrapper TU that includes PCSX2's headers first and then `#define`s three names works for
  microVU; keep that TU separate so adapter edits do not recompile the 10.6k-line JIT.

## 6. Interpreter vs microVU on the captures: P is wrong in the interpreter (EFU opcode table)

- **Seen:** `ob.sh vucompare`: 120/120 captures replay exactly in the offline interpreter; microVU equals it bit for
  bit on 64/120. Data memory, VF, VI, ACC, Q, I, R, CLIP and all 92 PATH1 packets (98,576 bytes) are identical in
  all 120; only P (20 captures), STATUS (40) and MAC (44) differ.
- **Found by:** `--verbose` diffs, then `--synthetic` programs: "ESIN P, vf1.x" with vf1.x = 0.5 gives
  interp P 0x3ef57743 (sin 0.5) and microVU 0x3fb504f3 (1/sqrt 0.5).
- **Cause (P, verified on the encodings):** PS2Recomp decodes four EFU ops at the wrong lower-special codes:
  ERSQRT 0x77 / ESQRT 0x78 / ESIN 0x79 / EATAN 0x7C / EEXP 0x7D (`ps2_vu1_lower.cpp:726-772`, same numbering in
  the latency table `ps2_vu1_core.cpp:1435-1477`), while PCSX2's recompiler and interpreter both have
  ESQRT 0x78, ERSQRT 0x79, ERCPR 0x7A, WAITP 0x7B, ESIN 0x7C, EATAN 0x7D, EEXP 0x7E
  (`pcsx2/x86/microVU_Tables.inl:59-101`, `pcsx2/VUops.cpp:3607-3660`). Outbreak's program at 0x220/0x640 has an
  ERSQRT that the interpreter runs as ESIN of a ~1e8 value: P = 0x7f7fffff; microVU's P equals the program's final Q
  (an RSQRT of the same value), as it should. So the interpreter is wrong, not microVU.
- **Cause (STATUS/MAC, by design):** microVU only computes flags that a later instruction reads
  (`mVUsetFlags`, `microVU_Flags.inl:113-135`; `noFlagOpts = false`, `microVU_Misc.h:265`), so at the E bit STATUS/MAC
  keep an older value; the interpreter computes every flag. In 49 captures the only differences are STATUS/MAC = the
  run's input value or P = final Q; in the other 7 (program 270f8e30, pcs 0x218/0x6b8) MAC holds a value from an
  earlier instruction (unverified without a trace, same mechanism expected). `--synthetic`: flags that are read
  (FMAND after a SUB) match; unread ones do not. `--no-flag-hack` changes nothing (not the vuFlagHack).
- **Fix (proposed, not done):** a PS2Recomp patch moving ERSQRT/ESIN/EATAN/EEXP to PCSX2's codes, with a test per op.
  Whether it changes Outbreak's picture on the interpreter path: unverified. microVU's stale flags matter only if a
  program reads flags it did not set (cross-program); the gate (plan step 5) decides.
- **Evidence:** `C:\ob\logs\vucompare-final.log`, `vucompare-x.log`; timing: interpreter 178-201 ns per VU1 cycle,
  microVU 0.72-0.98 ns (190-247x; weighted by the boot's own per-program cycles 189-227x), 4 runs; first run of a new
  program (compile) at most ~2 ms.
- **Take-away:** the differential test found an interpreter bug in its first run; bit-equality against the
  interpreter is a triage tool, not the verdict.
