# M5 sound: PCSX2's SPU2 in the runner

- **Date:** 2026-10-24
- **Who:** developer, Claude Code session
- **Goal:** sound on Windows and Android: the game's own sound drivers (already running on the IOP interpreter)
  talk to PCSX2's SPU2 in-process; output through raylib's audio (miniaudio: WASAPI, AAudio).
- **Outcome:** sound on Windows. PCSX2's SPU2 runs in the runner (library tests 7/7, PS2Recomp 0056); two PS2Recomp
  faults found by following the samples back: the EE's `SQRT.S` read the wrong register (0057: saturated music) and
  the IOP scheduler preempted equal-priority threads (0058: right-channel crackle, 45 -> 1.1 clicks/s against
  PCSX2's 0.9). Gate 3/3 pcsx2-sw, all suites green. Android not built with sound yet.
- **Versions:** PCSX2 v2.9.134 (`C:\ob\pcsx2`), PS2Recomp `C:\ob\up` d0bcc82 + 0056 `50ff3e0`, 0057 `dacdcf9`, 0058
  `9cbd463`, MSVC 2022, Windows 11.

## Summary

Step 0 confirmed the plan: the game's libsd writes the SPU2 registers itself (about 8,000 register writes and
8,192 DMA starts, almost all core 1 streaming, between boot and J's Bar), so PCSX2's SPU2 can be plugged in at the
register level, like the GS. The library (`native/pcsx2_spu2`) is PCSX2's SPU2 sources plus AudioStream with a
pull backend; patch 0056 adds a `Spu2Device` the IOP hands register accesses and SPU2 DMA to, with the device
deciding when transfers end. Two clock problems so far: a test buffer that filled before the sound arrived, and
PS2Recomp restarting its IOP cycle count at an IOP reboot.

## Struggles

### 1. Step 0: does the game touch the SPU2 itself?

- **Seen:** PS2Recomp HLE-implements some IOP modules (`ps2xIOP/src/modules/libsd.cpp`); if libsd were HLE, no
  register traffic would reach an SPU2.
- **Found by:** a throwaway counter in the build copy's `iop_memory.cpp` (`writeHardware32`, powers of two),
  `ob.sh check --tag step0`.
- **Cause:** none: the IRX modules are the game's own (14 loaded, `iopbuf:` and `cdrom0:\IOP\MODULES`).
- **Fix:** none needed; counter removed (the build copy compared equal to `C:\ob\up` afterwards).
- **Evidence:** `C:\ob\logs\boot-step0.err`: `spu2 writes=16384` (16-bit writes arrive as two byte writes, so
  about 8,000 register writes), `spu2 dma starts=8192 core=1`, one core 0 line.
- **Take-away:** the IOP memory model already knew libsd's block-transfer flag (`iop_memory.cpp:270-276`), a hint
  in the code itself.

### 2. SoundTouch would not compile with PCSX2's include paths

- **Seen:** `common/BitUtils.h(70): error C2039: 'has_single_bit'` and `memory.h` errors in SoundTouch.cpp.
- **Found by:** build log `C:\ob\logs\ob-spu2-build.log`.
- **Cause:** linking SoundTouch/freesurround to `ob_pcsx2_gs` (for its flags) gave them PCSX2's include paths;
  `pcsx2/Memory.h` shadows the system `<memory.h>` because Windows file names ignore case.
- **Fix:** both 3rdparty libraries keep their own include paths (`native/pcsx2_spu2/CMakeLists.txt`).
- **Evidence:** next build compiled them.
- **Take-away:** don't propagate PCSX2's include directories to third-party code.

### 3. Key-on test silent although the voice played

- **Seen:** `peak after key-on 0.0000` while the voice's envelope read 0x7FFF.
- **Found by:** reading back ENVX/VOLXL, then a temporary print of the stream's fill (`buffered=12000`).
- **Cause:** the test's first second of silence filled AudioStream's ring buffer; later samples were dropped
  until something read it. (Also a wrong test register: 0x18C is the wet left mix, dry right is 0x190.)
- **Fix:** the test pulls 256 frames per 256 samples, as the host audio callback does.
- **Evidence:** `ob_pcsx2_spu2_tests`: peak 0.9744, 5/5.
- **Take-away:** the output stream must always be drained; a hidden window that opens no audio stream leaves it
  full, which is harmless (writes are dropped) but means a measurement tap has to drain it.

### 4. A 119 GB tap file and a stalled game: the IOP cycle count restarts

- **Seen:** a throwaway WAV tap (drains the stream in `ob_spu2_advance`) wrote 119 GB and the game sat at tick 25.
- **Found by:** file size, `[fps] tick 25 | 0.0 fps`, then `iop_emulator.cpp:143` (`totalCycles = 0` in reset,
  called from `ps2_runtime.cpp:726`, `:1355`).
- **Cause:** when the game reboots the IOP, PS2Recomp's cycle count starts again at 0; the SPU2's clock read that
  as time running backwards (`TimeUpdate`'s sanity path moved `lClocks` back) and the samples-mixed count
  underflowed, so the tap looped writing.
- **Fix:** the adapter's clock never runs backwards (it adds the jump back to a base, `spu2_side.cpp` `SetNow`);
  the samples counter only adds forward moves; new test case (480 samples after a restart, next event in the
  restarted units); the tap got a size cap and lost its per-sample flush. The huge file was deleted.
- **Evidence:** `ob_pcsx2_spu2_tests` 7/7; tapped check 47 s wall, 136.9 s of audio for 8,264 ticks (137.9 s).
- **Take-away:** any device keyed to the IOP cycle count must survive the count restarting.

### 5. Tearing and peaking: the stream is distorted before the SPU2 gets it (fixed: PS2Recomp 0057)

- **Seen:** the developer heard tearing and peaking in the clips. Measured: no sample-to-sample jumps; the waveform
  sits flat at full scale in runs of up to 133 samples (J's Bar 14% of samples, menus 18%).
- **Found by:** throwaway probes, one per step back along the data path, each a 47-65 s `ob.sh check` run:
  1. muting one mix source at a time: the stream input alone causes it (muted, -22 dBFS, 0% clipped); voices and
     core 0 change nothing;
  2. the stream transfers (core 1, about 94 per second of 1,024 halfwords, every one finished on time) carry
     samples already at the limits (`8001 8001 8001 8001`, `7fff 7fdc ...`);
  3. that buffer (IOP 0x05BF60) is filled by PS2Recomp's HLE `memcpy` (`iop_sysclib.cpp:42`) from a 32-bit
     mix buffer at 0x05A080, built by the game's IOP code: clear (0x525E4), add each stream (0x52C84: plain add,
     >>1, >>2 or multiply by volume), clamp to ±0x7FFF (0x52CF4); the code is correct as read (capstone on an
     IOP RAM dump);
  4. each stream's 256 samples (0x1DE280..0x1DEA80, two streams at volume 0xFF) already peak at 32,768;
  5. those come by `memcpy` from rings at 0x1CA000..0x1D2000, which are written by SIF transfers from the EE
     (EE 0xE79D80..0xE81000, 1-2 KB blocks): the samples are made on the EE, in recompiled code.
- **Cause:** PS2Recomp's recompiler translated the R5900's `SQRT.S fd, ft` with fs as the source
  (`ps2xRecomp/src/lib/fpu_translator.cpp:61`). The EE reads ft (bits 20-16); PCSX2's `SQRT_S` takes
  `sqrt(fabs(Ft))`, and the runtime's own helper comment says `sqrt(|ft|)`. The game's ADX filter setup
  (0x126250: cutoff and sample rate -> two predictor coefficients) takes sqrt(2) as `sqrt.s $f20, $f22`
  (0x12626C) and a second root as `sqrt.s $f0, $f12` (0x126328); both compiled to `sqrt(f0)`, so the
  coefficients came from leftover register values: 8553/-4465 for the first stream (usable by luck), then
  8192/-4096 (2.0/-1.0), a predictor that runs away to the limits. Found by: a write watch on the EE ring
  (page protection + vectored handler reading the EE context's pc: writers 0x127C0C/1C/90/98 in the decoder
  0x1279C0, called from 0x134E68), then a print of the decoder's inputs (key 0, scales 0x0C-0x143 sane,
  coefficients 8192/-4096), then the coefficient function's disassembly (`c1 0x160504`: the disassembler did
  not know the EE form either).
- **Fix:** PS2Recomp 0057: SQRT.S reads ft. Test `R5900 SQRT.S reads ft, not fs` (ps2x 535/535; without the
  fix 534/535, `C:\ob\logs\ob-0057-without.log`). Recompile: 2 generated files changed (0x126250, plus the
  decoder losing its probe), runner 29 s.
- **Result:** J's Bar about -17 dBFS, peaks below full scale, 0.000% clipped (menus 38-46 s and J's Bar
  82-137 s; was 14-18%). Clips `C:\ob\logs\spu2-fixed-{menu-36-48s,jsbar-82-100s}.wav` sent to the developer.
  Gate (`PS2X_GS=pcsx2-sw`, SPU2 on): savedata, access, capcom GREEN at max 0; advisory screens as before.
- **Other uses:** the whole game has 3 `sqrt.s` sites in the main ELF; all were wrong the same way.
- **Tried and taken back:** LWL/LWR in the IOP interpreter merging into a pending load of the same register (the
  R3000 forwards it); no change to the level, so not kept.
- **Evidence:** `C:\ob\logs\boot-{muteinp,spu2dma,memcpy,mix,memcpy2,pcmw3,sif}.err`, `C:\ob\logs\iopram.bin`.
- **Take-away:** follow the samples backwards one buffer at a time; PS2Recomp's HLE `memcpy` hides who wrote what
  (byte writes from C++, not guest stores).

### 6. Two process slips while verifying

- **Gate run on the wrong renderer:** `ob.sh gate` without `PS2X_GS=pcsx2-sw` boots the CPU GS (the unfixed
  fallback, `[gs] backend=cpu`), which is red on every screen; I read that as a regression and spent two runs
  bisecting (SPU2 off; old sqrt lines) before seeing the backend line. The gate's documented run is
  `PS2X_GS=pcsx2-sw`; with it: 3/3 green.
- **Recompile 22.5 min:** `ob.sh tools && ob.sh recompile` for a one-line recompiler change took 22 min 30 s
  (`C:\ob\logs\ob-0057-recompile.log`), past the five-minute ceiling, although only 2 of 10,497 generated files
  changed and the runner rebuilt in 29 s. The time is in regenerating every function of the main ELF and all
  overlays. Open: a build-setup defect to fix (cache the analysis, or regenerate only what the change touches).
- **Probe hygiene:** a page-protection watch must cover whole host pages (EE RAM starts at host offset 0x40, so a
  guest page spans two host pages; the first version crashed on the second).

### 7. Right-channel crackle: the IOP scheduler preempted an equal-priority thread (fixed: PS2Recomp 0058)

- **Seen:** "still cracking". Click detector: 40.9 clicks/s (PCSX2 0.9), right channel almost only, already in the
  stream data the IOP hands the SPU2 (entry 5's crackle notes).
- **Found by:** an ordered event log (decoder, copy-back, CRI transfer routine, SIF sends, one shared sequence
  counter) showed one EE context does all of it, so the EE side is in program order; CRI's SJ ring objects for left
  (0x207220) and right (0x207260) then drift apart in our build (right write position 0x400, later 0xB40 behind) while
  PCSX2 keeps them identical (2,910 PINE samples in J's Bar, 98.6% equal, the rest one-chunk transients); the first
  divergence (cycle 321 of the transfer routine): equal EE data, IOP free space 0x800 left vs 0x400 right, swapped the
  next cycle: the IOP built its status (one 2,176-byte IOP->EE transfer, return 0x50588) between the mixer's left and
  right bookkeeping. PS2Recomp's IOP kernel chose the next thread every 256-instruction slice by priority then lowest
  id (`iop_kernel.cpp` `beginNextReady`), so a lower-id equal-priority thread that became ready took over mid-work;
  the real IOP thread manager only switches when the running thread blocks or rotates, or a higher priority wakes.
- **Fix:** 0058: per-priority ready queue in readiness order (`queueNewlyReady`), the last-run thread keeps the head,
  RotateThreadReadyQueue and ChangeThreadPriority move a thread to the tail. Test `testThreadReadyQueue` (fails without:
  "an equal-priority thread took over the running thread at the end of its slice"). A first version queued threads
  only at scheduling time and put a rotating thread ahead of one that became ready during its slice; the test caught it.
- **Evidence:** J's Bar clip window 45.2 -> 1.1 clicks/s; stale right-ring starts 59/383 -> 0/599; later scene 5.7/s
  through AAC vs PCSX2's 3.6/s, both right-heavy (scene content: right-panned effects; PCSX2 13 left / 162 right).
  Gate 3/3 pcsx2-sw at max 0; J's Bar check 50 s wall (unchanged); ps2x 535/535, iop 5/5, gs_cache 45/45, ob_diag 23/23,
  pcsx2_vu 3/3, pcsx2_gs 84/84, pcsx2_spu2 7/7 (now in `ob.sh test`). 0056's own "fails without" run (old routing and a
  stubbed setter): "SPU2 register reads and writes (8/16/32-bit) must reach the external device".
- **Take-away:** compare state with the reference emulator (PINE) as soon as a divergence is suspected; an HLE kernel's
  scheduling rule is part of the machine's timing.

## Still open

- After the fix the developer hears "a tiny bit of buzzing, but better". Measured: no 187.5 Hz (block-rate)
  peak, no clicks at the 256-sample block joins (step size flat across block phase within 12%), decoder
  coefficients now 7400/-3342 on every stream (the ADX formula for a 500 Hz cutoff at 48 kHz). Candidates left:
  AudioStream's time stretch (A/B clip with `SyncMode = Disabled` sent), or the game's own ambience. The developer
  pointed at 8-10 s of the J's Bar clip (capture 90-92 s): a 72.5 Hz component (-37.9 dB) with 37.5 Hz, from the
  stream (the voices-only capture lacks it). **It is in the original:** a PCSX2 recording of J's Bar (driven by
  keyboard with the developer's permission, temporary key bindings and a capture hotkey, restored afterwards;
  `ps2_emu/videos/...20261025091558.mp4`, audio via ffmpeg) has the same strongest low component, 72.5 Hz at -38 to
  -43 dB, and the same 57-60 Hz content. Reference clip `ps2_emu/audio-clips/pcsx2-reference-jsbar-18s.wav`.
  The developer still heard more buzz in ours than in PCSX2's clip. Cause: my measurement tap. It drained every
  sample as soon as it was mixed, so AudioStream's time stretch (SoundTouch) always saw a near-empty buffer and kept
  splicing; the tapped captures carry a 37.5 Hz component that the stretch-off capture and the PCSX2 recording
  (taken before its stretch) do not. The live output (a temporary hidden-window audio switch plus a recording of
  exactly what the audio device pulls, `ob.sh check --paced`, 140 s) has no 37.5 Hz component; its 72.5 Hz is
  below the tap's. Live clip `ps2_emu/audio-clips/spu2-live-jsbar-82-100s.wav`. Two 20 ms dropouts in 55 s of
  J's Bar (83.08 s, 107.92 s); the second coincides with the script's load60s frame capture (a game stall), the
  first is unexplained.
  The developer still hears more buzz in the live clip than in PCSX2's. Ruled out since:
  1. EE ADX decode: bit-exact. 12 decoder calls (20,416 samples) recorded in J's Bar (compressed input, history,
     coefficients, the game's low-nibble table at 0x21B868, then what the call wrote) match an independent Python
     decode of the same input, 0 mismatches.
  2. Stream delivery to the SPU2: core 1 auto-DMA never starved (0 samples in 130 s), about 94 refills/s.
  3. Time stretch in normal play: a paced run recorded both before the stretch (PCSX2's own capture point,
     `GSCapture::DeliverAudioPacket`) and at the audio device: spectrally identical.
  Comparison with PCSX2 on the same scene (not sample-alignable: dialogue timing differs): octave-band balance
  within scene-to-scene variation; one real difference: PCSX2's J's Bar never goes below -28 dB (a steady bed at
  110/220 Hz), ours has near-silent moments (-73 dB at 163 s): a continuous layer (ambience loop or music) may be
  missing or stopping in ours. Unverified. Fair A/B clips (both before the stretch, same scene point):
  `ps2_emu/audio-clips/ours-jsbar-scene-18s.wav`, `pcsx2-reference-jsbar-18s.wav`.
  Further checks (the developer asked for research; web: nothing specific to Outbreak, ADX or PS2Recomp audio;
  leads: PCSX2's SPU2-timing write-up, a DeSmuME report of stream pops from timer/audio clock mismatch):
  4. EE-to-IOP music rings: 12,000 blocks copied out by the IOP mixer, 0 repeats of stale content.
  5. IOP mixer per cycle: stereo music (full volume, panned L/R) plus a mono layer at 0xAA to both sides.
  6. SPU2 voices: two looping ambience voices play throughout J's Bar; many effects are hard-panned; overall L/R
     balance matches PCSX2 (+0.1 dB vs +0.4 dB). PCSX2's L/R correlation is lower (0.15 vs 0.36).
  7. Reverb: the game sets core 1 effect volume 0 in J's Bar (`SdrSetRev(1, 4, 0)` from 0x1B7E90, depth from the
     room data via 0x394F14 = 0x80000000 | data[+8], written by GAME overlay 0x543D40). PCSX2 holds the same
     values there (read over PINE: 0x394F10 = 1, 0x394F14 = 0x80000000), so reverb off is the real game's choice.
  8. The PCSX2 clip went through its capture's AAC encoder (LC, ~150 kbps); ours was uncompressed. Our clip passed
     through the same AAC sent for a like-for-like listen: `ours-jsbar-scene-18s-aac.wav`.
  **Crackle found (the developer: "still cracking"):** a click detector (|second difference| > 12x the local median)
  gives 40.9 clicks/s for our J's Bar clip against 0.9/s for PCSX2's. Followed back:
  - right channel only (2,795 right vs 14 left), at fixed block phases;
  - already in the stream data the IOP hands the SPU2 (raw transfer dump: right 13.6/s, left 0.7/s), so not the chip;
  - the IOP mixer's music-right input carries it (47 bad joins in 1,470 blocks; music-left 2); the EE decoder's history
    carries over correctly between calls on both channels; decoder left/right destinations always 0x40C0 apart;
  - CRI's EE rings (SJ ring objects, `chan 0x1FE188/0x1FE1C8`): left 0xE79180, right 0xE7D240, 0x4000 bytes + 0xC0
    extra each; the decoder spills 0x38 bytes into the extra area at the end of a lap and the ring code copies them
    back to the start (`func_1251C8` via `func_1253D8`/`func_125258`, both channels);
  - **at transfer time** (CRI's transfer routine, return 0x13867C, EE thread 3) the right ring's start does not yet
    hold that copy in 59 of 383 sends that cover it (only sends starting at the ring base and longer than 1 KB);
    the left ring's start is always current (0 of 383). The IOP gets 28 stale samples at the start of the right
    ring on those laps: a click about 6 times a second.
  Cause: an ordering difference between CRI's stream state machine (which does the copy-back) and its transfer
  thread in our build; on the real game (PCSX2: 0.9 clicks/s) the copy precedes the send. Not yet found why; the
  runtime does not honour the EE's interrupt-enable bit (`di`/`ei` flip `cop0_status` but nothing checks it), one
  candidate class of scheduling difference. Tried and taken back: handing the SPU2 a snapshot of each transfer (no
  change: the damage is in the data before the transfer starts).
