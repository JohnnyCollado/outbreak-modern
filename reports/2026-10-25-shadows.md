# Broken character shadows (stairwell, storage room)

- **Date:** 2026-10-25
- **Who:** developer (drove every run), Claude Code side session
- **Goal:** find why the floor patch under each character shows smeared texture fragments instead of a soft dark
  shadow in the first stairwell and the storage room (scenario "Outbreak", after J's Bar), and fix it.
- **Outcome:** fixed. Three PS2Recomp stand-ins for Sony's libvu0 differed from the game's own code: 0062
  `sceVu0RotTransPers(N)` (`mode` read backwards: shadow-volume z x16), 0063 `sceVu0InnerProduct` (added w),
  0064 `sceVu0MulMatrix` (product in the other order). The developer: stairwell and storage-room shadows "look
  solid, like PCSX2". Tests 541/541, all suites green; gate 3/3 (`PS2X_GS=pcsx2-sw`).
- **Versions:** outbreak-modern `98370b1` (PS2Recomp `eb8688b` + 0001-0061 -> 0064, PCSX2 v2.9.134 GS), Windows 11.

## Summary

The game draws character shadows as stencil shadow volumes counted in colour: a 16-bit buffer, volume faces added
or subtracted with a depth test against the room, then one darkening pass. The volumes are built on the EE (SUBMAIN
`0x347D60`) and sent as PATH2 packets, which is why every GS, VU1 and display A/B kept the fault. A/B runs ruled
out the renderer, VU1, the GS thread, mods and the adapter; GS dumps of our frame and PCSX2's showed the volume
z 16x too large and the volume shapes broken. The builder uses four HLE libvu0 stubs; checked against the game's
own libvu0 code (disassembled from the disc image), three were wrong. 0062 put the shadows in place; 0063/0064
made them solid. Developer-driven visible runs plus logs and GS dumps were what got this done: steering a
hidden run there blind did not.

## Struggles

### 1. Reaching the stairwell from a hidden run

- **Seen:** the pad-pipe run (`ob.sh boot --pad`) reached J's Bar gameplay, but steering Kevin blind with one
  screenshot per step never left the room (room id `0x003065AA` stayed 1), and Kevin died to the zombies while
  waiting.
- **Found by:** shots in `C:\ob\frames-shadow1`.
- **Cause:** fixed cameras change with position; tank controls; no position readout.
- **Fix:** the developer drives visible runs; the session reads logs. Launchers `C:\ob\play-ab*.bat` (not in git)
  set one variable each.
- **Evidence:** `C:\ob\frames-shadow1\g1..n2.png`, `p0.png` (YOU DIED).
- **Take-away:** for scenes past J's Bar, a human-driven visible run plus logs is far faster than blind pad steps.
  J's Bar draws no character shadows at all (`C:\ob\frames-shadow1\k1.png`), so it cannot stand in.

### 2. A/B runs: every backend shows the fault

- **Seen:** broken shadow in all runs.
- **Found by:** developer screenshots + logs `C:\ob\logs\boot-ab-*.log/.err` (`[gs] backend=`, `[vu1] backend=`,
  `gs thread off`, `[settings]`, `[pnach]` lines confirm each run's settings).

  | Run | GS | VU1 | GS thread | Mods / pack | Shadow |
  |---|---|---|---|---|---|
  | developer's play | pcsx2-vk | mvu | on | widescreen, pack | broken |
  | sw | pcsx2-sw | mvu | on | widescreen, no pack loaded (`replacements=none`) | broken |
  | interp | pcsx2-vk | interp | on | widescreen, pack | broken |
  | nothread | pcsx2-vk | mvu | off | widescreen, pack | broken |
  | control | pcsx2-vk | mvu | on | widescreen, pack | broken |
  | nomods | pcsx2-vk | mvu | on | no mods (`mods=-`, aspect Auto 4:3), pack | broken |
- **Cause:** not in PCSX2's renderers, microVU, the GS thread, texture replacement or the widescreen patch.
- **Evidence:** the logs above (run 2026-10-25 17:02-17:26).
- **Take-away:** the reference PCSX2 runs the SW renderer (`ps2_emu/inis/PCSX2.ini:228`, `Renderer = 13`), the same
  GS code we run, so a fault common to every backend points upstream of the GS.

### 3. No GS readback

- **Seen:** the shadow could have been made by reading the GS back to the EE (a common PS2 trick).
- **Found by:** the adapter's `gs thread:` stats line: `sync waits 0` over 9,000 vsyncs in every run, and readback
  (`GS::consumeLocalToHostBytes`, `gs_frontend.cpp:1694-1702`) goes through `ob_gs_read_local`, which is a sync
  wait in threaded mode.
- **Cause:** the game makes the shadow on the GS side only (render to texture).

### 4. The adapter's dropped cut units are not it

- **Seen:** `pcsx2_side.cpp:468-477` silently drops a cut GIF unit that is not IMAGE; a lost silhouette draw would
  leave stale VRAM where the shadow samples.
- **Found by:** a temporary probe (not committed, removed) logging each drop; developer run into the stairwell.
- **Cause:** one drop in the whole run, early, PATH2, 64 B, whose "tag" words are VIF codes (`0x13000000` FLUSHA,
  `0x50000002` DIRECT): a one-off VIF1 parse slip, not the per-frame shadow fault.
- **Evidence:** `C:\ob\logs\boot-ab-pcsx2-vk-mvu-t1.err` (17:35), line `[shadowprobe] drop #1 path=2 ...`.

### 5. GS dumps: the shadow is stencil shadow volumes, and ours are broken

- **Seen:** need the GS command stream of one stairwell frame, ours and PCSX2's.
- **Found by:** temporary capture (not committed): PCSX2's own uncompressed dump writer (`GSDump.cpp` lines 19-165,
  without the xz/zstd writers) built into `ob_pcsx2_gs` in place of the stubs, triggered by F9 or the file
  `C:\ob\gsdump\trigger` in the adapter's vsync. Reference: PCSX2 2.9.134 (`ps2_emu`, SW renderer) single-frame dump
  with `GSDumpCompression = 0` and the hotkey on F9 (ini backed up as `PCSX2.ini.bak-20261025-shadow`). Readers
  written for the session: a `.gs` parser (format `pcsx2/GS/GSDump.h`), a GIF walker (draw batches per
  FRAME/TEX0/ZBUF/ALPHA/TEST, IMAGE uploads, GS vertex queue), a net-coverage rasteriser.
- **What the frame does (both):** clears a 512x448 CT16S buffer at block `0x2a20`; draws untextured volume faces into
  it with ALPHA `0x68` (Cs + Cd, add) or `0xA1` ((Cd - Cs) * FIX, subtract), depth test GREATER against the room's
  Z32 buffer at `0x1c00`, Z writes off (`TEST=0x70000`, `ZMSK=1`); then one full-screen sprite samples `0x2a20` as a
  CT16S texture and darkens the frame (ALPHA `Cd - Cs * 0x21/128`). Stencil shadow volumes, counted in colour.
- **Cause (so far):** with depth ignored, the net add/sub count of the reference's volumes is one clean character
  silhouette (the far cap); ours is the same silhouette in fragments, some subtracting
  (`C:\ob\gsdump\net-pair.png`). Some volume faces get the wrong add/sub choice or wrong corners in our build.
  Volume extents match (x ~50-330, y ~150-390 px), so the geometry is broadly right.
- **Evidence:** `C:\ob\gsdump\ours-1..8.gs` (our stairwell), `ps2_emu\snaps\...20261025200949.gs` (reference),
  `C:\ob\gsdump\net-ref.png`, `net-ours4.png`. Side note: the reference re-uploads textures every frame (63
  IMAGE transfers into `0x3120+`); ours uploads none in the frame (textures resident at `0x3120-0x3fc0`). Not near the
  shadow buffer (it ends at `0x3120`); unexplained.

### 6. The cause: PS2Recomp's sceVu0RotTransPers(N) stand-ins read `mode` backwards

- **Seen:** the volumes' add/sub always follows screen winding (add = counter-clockwise) in both frames, 0
  exceptions in 4 dumps, so the facing decision is right; the volume corners' screen x/y match the reference, but
  their 24-bit z is about 16x too large in ours (near corner `0x0c84b0` vs `0x00c305`, far `0x06d1da` vs
  `0x006c98`): a 4-bit shift. The depth test against the room (`ZTST` GREATER) then passes the wrong pixels.
- **Found by:** a probe counting the shadow state per GIF path (temporary, not committed): the volumes travel on
  PATH2 (per stairwell period ~1,070 PATH2 packets each set FRAME `0x2a20`; PATH1/3 flat), i.e. EE-built
  packets through VIF1 DIRECT, so VU1 never touches them (why both VU1 backends showed it). x16 = the GS 12.4 fixed
  point (VFTOI4) applied to z, which should be an integer (VFTOI0). The game links Sony's libvu0; PS2Recomp replaces
  `sceVu0RotTransPers@0x0017FAD0` and `sceVu0RotTransPersN@0x0017FA08` with C++ stubs (`C:\ob\work\decomp.toml:219-220`).
- **Cause:** the game's own code (main ELF, read from the disc image): RotTransPersN keeps `mode` (`$t0`) in `$s0`
  (`0x17fa38`), then `beq $s0, $zero, +2` (`0x17fa6c`) with `vftoi4.xyzw vf10, vf9` in the delay slot (`0x17fa70`,
  always runs) and `vftoi0.zw vf10, vf9` after it (`0x17fa74`, skipped when mode == 0). RotTransPers is the same
  (`mode` = `$a3` -> `$s0` at `0x17faf8`; `0x17fb2c`-`0x17fb34`). So mode == 0: z and w x16; mode != 0: z and w
  plain integers. The stubs take `fullFtoi4 = (mode != 0)` (`ps2xRuntime/src/lib/Kernel/Stubs/VU.cpp:892`, `:909`):
  inverted. Their tests (`ps2xTest/src/ps2_vu_tests.cpp:759-865`) encode the same inverted rule.

- **Fix:** PS2Recomp 0062 (`C:\ob\up` `5e0950f`): both stubs take `fullFtoi4 = (mode == 0)`; tests use Sony's
  mode, plus RotTransPers/RotTransPersN "ftoi0_z_when_mode_nonzero". Without the fix 534/539
  (`C:\ob\logs\ob-0062-without.log`), with it 539/539 and every suite green (`ob-0062-with.log`).
- **Result:** after-fix dumps (`C:\ob\gsdump\ours-1.gs`, `ours-2.gs`, 23:28/23:32) have volume z on PCSX2's scale
  (near `0x00c9c3`, far `0x006e89`); the shadows sit under and behind the characters, away from the lamp; the smear at
  the lower-left wall is gone (`C:\ob\gsdump\shadow-before-after.png`). The developer: "it is still a bit fuzzy".

### 7. Still patchy: two more libvu0 stubs differ from the game's code

- **Seen:** after 0062 the shadows are in place but broken into patches with gaps; PCSX2's is one solid silhouette
  (`C:\ob\gsdump\shadow-zoom.png`). The depth-free net coverage shows the same patches (struggle 5), so it is a
  second fault in the volume corners, independent of z.
- **Found by:** the only caller of `sceVu0RotTransPers` is SUBMAIN `0x00347D60` (the shadow-volume builder); it calls
  the stubs ApplyMatrix (5x), RotTransPers (2x), InnerProduct (2x), MulMatrix (1x). Each compared with the game's
  own libvu0 code (a small EE disassembler written for the session, `eedis.py` in the session scratchpad):
  - ApplyMatrix `0x17E80C`-`0x17E830`: matches the stub.
  - **InnerProduct** `0x17E994`-`0x17E9A4`: `vmul.xyz`, `vaddy.x`, `vaddz.x`: x, y, z only. The stub adds `w*w'`
    (`VU.cpp:557`); for points with w = 1 every dot product is 1 too large.
  - **MulMatrix** `0x17E88C`-`0x17E8C4`: each row i of the third argument transformed by the second:
    `out[4i+j] = sum_k a2[4i+k] * a1[4k+j]`. The stub's `mulVuMatrix(a1, a2)` gives `sum_k a1[4i+k] * a2[4k+j]`
    (`VU.cpp:86`, `:706`): the product in the other order.
  - DropShadowMatrix `0x17F878`-`0x17FA04` (not called by the builder): matches both modes up to rounding.
  - InnerProduct and MulMatrix have exactly one caller in the whole game: the shadow builder.
- **Fix:** PS2Recomp 0063 (`c3db3d2`): InnerProduct sums x, y, z; 0064 (`ba78d2f`): MulMatrix
  `mulVuMatrix(arg2, arg1)`. Tests InnerProduct_ignores_w, MulMatrix_transforms_arg2_rows_by_arg1, and the two
  older tests corrected to libvu0. Without both 538/541 (`C:\ob\logs\ob-0063-0064-without.log`), with 0063 only
  539/541 (the two MulMatrix tests), with both 541/541 and every suite green (`ob-0064-with.log`).
- **Result:** gate 3/3 green on the 0062 build and on the final build (`.run/logs/ob-gate-0062.log`,
  `ob-gate-0064.log`); developer run: stairwell and storage-room shadows solid, like PCSX2.
- **Take-away:** PS2Recomp's HLE libvu0 (commit 6970f3a upstream) was written from descriptions ("reconstructed
  from behavior; not claimed bit-exact", `VU.cpp:447`), and its tests encode the stubs' own reading. The game links
  the real library, so each stub can be checked against the disc: compare before trusting one.
