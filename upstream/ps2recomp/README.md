# Changes for PS2Recomp

Fixes made while building on [PS2Recomp](https://github.com/ran-j/PS2Recomp) (GPL-3.0), one per
fix, so each can go upstream as its own pull request, **only with your OK**. They live as commits
in `C:\ob\up` (the repo's old vendored copy was removed on 2026-10-22). Apply them in order with `git am` on PS2Recomp `eb8688b`. Each patch builds on its own and
adds its own test.

| Patch | What | Reference for the right behaviour |
|---|---|---|
| 0001 | Linux (any GCC/Clang x86-64) builds failed: SSE4.1 intrinsics without the target enabled. Adds `-msse4.1` next to the existing ARM flags. | build error |
| 0002 | BLEZ/BGTZ/BLTZ/BGEZ (and -L/-AL) compared 32 bits; the R5900 compares the 64-bit register. | PCSX2 `Interpreter.cpp` (`GPR.r[rs].SD[0]`) |
| 0003 | CVT.W.S rounded instead of truncating; CVT.W.S/TRUNC.W.S didn't saturate. The out-of-range cast was undefined and **gave different results on x86 and ARM**. | PCSX2 `FPU.cpp` `CVT_W` |
| 0004 | VU0 VRSQRT ignored fs. VDIV by zero gave 0. VSQRT clamped negatives to 0. Now uses the same PS2 float helpers as the EE FPU. | the repo's own ps2autotests-checked helpers |
| 0005 | VU0 LQI/SQI/LQD/SQD/ILWR/ISWR used EE RAM instead of VU0 data memory. SQI/SQD had fs/it swapped. VI0/VF0 could be written. VILWR/VISWR addressed `vi << 2` and ignored the field. A 5-bit VI index could write past `ctx->vi[16]`. | PCSX2 `VUops.cpp` `_vuLQI`, `_vuSQI`, `_vuLQD`, `_vuSQD`, `_vuILWR`, `_vuISWR` |
| 0006 | `fioOpen` and the rest of the VFS joined PS2 paths with exact case. On Linux/Android, `cdrom0:\IOP\MODULES\DRIVE.DAT;1` missed a disc copy named `iop/modules/drive.dat`, and Outbreak's boot retried forever. Now an exact-case miss falls back to matching each component ignoring case; Windows is unchanged. Found by booting Outbreak. | PS2 paths are case-insensitive (ISO 9660) |
| 0007 | `sceSifLoadModuleBuffer`/`LoadStartModuleBuffer` read the module from **EE** RAM, but a PS2 game passes an **IOP** address (Outbreak DMAs DRIVE.DAT to IOP 0x120000 first), so every load failed. IOP RAM is now read first, falling back to EE RAM. Buffer loads are recorded like path loads and named after their `.iopmod` name. `_sceSifLoadModule`/`_sceSifLoadModuleBuffer` write the start result to `*$a3`; `sceSifSearchModuleByName` added. | the game's own wrappers (disassembled) and the decomp's `sys.c`/`iop.c` |
| 0008 | The IOP interpreter had no `thmsgbx` (message boxes). Outbreak's sound driver creates one at start-up, so it never registered its RPC server and the game retried `SdrBind` forever. Ordinals 4-9, 11, 12; FIFO/priority order; error codes as on hardware. | ps2sdk `thmsgbx.h`/`thmsgbx.c`, `kerr.h` (behaviour only, reimplemented) |
| 0009 | `sceCdLayerSearchFile` (dual-layer DVD search) had no handler, so CRI's DVD file system waited forever. Layer 0 = `sceCdSearchFile`; layer 1 = not found (a folder of files has one layer). | — |
| 0010 | `CreateThread`/`ChangeThreadPriority` rejected priority 0 (`KE_ILLEGAL_PRIORITY`), although EE priorities are 0-127 and the runtime itself starts the main thread at 0. CRI ADX creates its server threads with the main thread's priority, so none existed and Outbreak's file system never finished loading. | ps2sdk `ee/kernel/src/thread.c` (`InitThread` creates `KernelTopThread` at priority 0 and checks for failure), `kernel.h` `MAX_PRIORITY 128` |
| 0011 | `ChangeThreadPriority` returned `KE_OK`; the EE kernel returns the **previous** priority. CRI ADX's lock/unlock saves and restores it, so every unlock put Outbreak's main thread at priority 0 and ADX's server thread never ran. | the game's own ADX lock/unlock (disassembled: the return value is stored and passed back) |
| 0012 | The **analyzer** replaced every "store into an executable section, then `j`/`jal`" with a NOP in the generated config, as possible self-modifying code. Outbreak's ELF has one executable section over code and data, so all 37 hits were ordinary data writes; 34 took effect and one hung the boot (a NULL transfer buffer). Now they are only printed and listed as commented-out lines in the TOML for review; nothing is replaced. Details: `results/analyzer-nops-20261021.md`. | the analyzer's own README ("flagged but requires manual review") |
| 0013 | `sceDmaRecvN` was a TODO stub that stops the program. Now sets MADR/QWC and starts a normal-mode transfer into memory, as libdma does; Outbreak uses it to copy the scratchpad to RAM. | the game's own `sceDmaRecvN` (disassembled) |
| 0015 | **IOP:** `sceSifGetOtherData` (sifcmd 23, the IOP reading EE memory) was a stub returning 0; it now copies EE → IOP. SPU2 DMA completed in `max(words×2, 64)` IOP cycles with the channel's MADR never moving; **block** (streaming) transfers, which libsd marks via `0x1B0 + core×1024`, now take the SPU2's playback time (192 cycles per byte = 48 kHz × 2 ch × 16 bit) and MADR advances at completion. Outbreak's ADX streaming thread (prio 39) never blocked and starved the sound driver's bank-upload worker (prio 50); the game polled the driver forever. Details: `results/sound-bank-wall-20261021.md`. | ps2sdk libsd `block.c`/`freesd.c`/`voice.c` (what the driver reads: `sceSdBlockTransStatus` returns MADR; the 0x1B0 mark); the SPU2's 48 kHz stereo 16-bit streaming rate; PCSX2's thread table and timings for the same game |
| 0016 | Games built with later SCE SDKs read the controller through **libpad2** sockets (`scePad2CreateSocket`/`GetState`/`Read`/`GetButtonProfile`, on libdbc); PS2Recomp only served libpad, so Outbreak's socket never connected and its first "press a button" screen (the memory-card prompt) waited forever. The nine `scePad2*`/`sceDbc*` entry points are now runtime stubs: each socket is a libpad port opened in DualShock 2 mode (same keyboard/gamepad backend, test override and debug snapshot); `scePad2Read` returns libpad's bytes from offset 2 (buttons active-low, sticks, 12 pressures), length 18. Not covered: the libdbc actuator (vibration) requests, which still run as the game's own code (an RPC to a server that doesn't exist; in Outbreak's boot it returns and the game goes on reading the pad; whether it vibrates is unverified). | the decomp's `padread.c`/`input.c` (how Outbreak uses the API: flag 2 sockets, `GetState == 1`, profile `& 0xFFF00000` = DualShock 2, `buttons = (d[0] << 8) \| d[1]`), its `D_002135A0`/`D_00223790` tables (which byte is which button), and the game's own `scePad2Read` (disassembled: it returns the data length) |
| 0017 | **Runtime: guest modules.** A game's code overlays (loaded by the game at run time, several possibly at one address: Outbreak's DEMO, GAME and NETWK all at 0x540000) had no place in the single function table, so the first call into one was a missing function. A `PS2GuestModule` is a separately recompiled image with its own table and a fingerprint (bytes expected at a guest address); `hasFunction`/`lookupFunction` fall back to the registered module covering the address whose fingerprint matches guest RAM. The main table keeps priority. Every path from a guest address to code (dispatch, threads, callbacks, RPC) goes through those two calls. | the game's own loader (`overlay.c`: copies the whole image, header included, to its load address; `MWo3_Init`, disassembled, only clears bss and runs the static-init range, so the header stays intact as a fingerprint) |
| 0018 | **Recompiler: `module = "<name>"`.** Builds the input as such a module: generated names and files get a `<name>_` prefix (overlays sharing addresses link into one binary), headers are `<name>_recompiled_functions.h`/`_stubs.h`, and `<name>_register_functions.cpp` fills the module's own table and registers it, fingerprinted by the first 64 bytes of its lowest loaded section. Without `module` the output is unchanged. Our `tools/mwo3_to_elf.py` wraps Metrowerks MWo3 overlays as ELFs (header as an allocated `.mwo3` section at the load address) so the recompiler can read them. | — |
| 0014 | The runtime kept its own guest memory (SIF RPC packet and server pools, TLS pool, boot-mode pool, callback stacks) at 0x1F00000-0x2000000 and capped every heap at 0x1F00000. On hardware that RAM is the game's: `SetupHeap(base, -1)` ends the heap at the thread's stack pointer, and ps2sdk's crt0 puts the stack at the top of RAM. Outbreak mallocs 22 MB + 1.1 MB; the second returned NULL and the font read into address 0 never finished. The runtime's memory now lives in the EE kernel's area 0x80000-0x100000 (`PS2_RUNTIME_RESERVED_*`); `SetupHeap(-1)` ends at the stack `SetupThread` recorded; an explicit size is honoured up to the end of RAM. | ps2tek (SetupHeap: "if heap == -1, the end of the heap resides at the thread's stack pointer"), ps2sdk `crt0.c`/`linkfile` (`_heap_size = -1`, `_stack = -1`) |

## Known gaps, not fixed here

- **VU DIV-by-zero value.** PCSX2's VU interpreter returns ±0x7F7FFFFF for VDIV/VRSQRT by zero;
  these patches give ±0x7FFFFFFF, the EE FPU's value. Which one VU0 hardware gives is **unknown**.
  ps2autotests (or a real PS2) would answer it.
- The VU0 MAC/status flags are still not updated by macro-mode ops.
- The EE FPU still rounds to nearest; the hardware rounds toward zero (`m0-decision.md`).
- The GS cache tests aren't registered with CTest in the top-level build (only `include(CTest)`
  when the folder is built standalone).
