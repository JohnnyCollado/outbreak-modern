# Q-register scan: does Outbreak read Q before a divide finishes?

**Answer: no.** All 42 VU0 divide/square-root instructions in File 1 are followed by a `VWAITQ`
before any read of Q, on every path. So writing Q at once (PS2Recomp) or after the hardware's
latency gives the same game behaviour, and **Q timing doesn't need modelling for Outbreak**.

Question raised 2026-10-21: on a PS2, VDIV/VSQRT/VRSQRT take several cycles and Q keeps its old
value until they finish. An emulator or recompiler that writes Q at once behaves differently
**only** if the program reads Q before the result is ready.

## Input

Your files, never committed: SLPM-65428 v1.04 with the English fan patch v2.1. All 9 binaries
match the decomp's sha1 lists (`config/SLPM_654.28/build.sha1` for the 5 the patch doesn't
change, `english.sha1` for the 4 it does: `SLPM_654.28`, `DEMO.BIN`, `GAME.BIN`, `NETWK.BIN`).

Tool: `tools/q_scan.py` (tests: `tools/test_q_scan.py`, 16/16 pass), rabbitizer 1.16.2 as the
R5900 decoder. Main ELF code range 0x100000-0x1d9b00 (decomp LAYOUT.md); overlay text sections
from their MWo3 headers.

## Results

Forward, from each producer, following both sides of branches, for up to 32 instructions:

| Binary | VU0 ops | Producers | VWAITQ first | Early read | Unresolved |
|---|---|---|---|---|---|
| SLPM_654.28 (main) | 1,264 | 42 (27 vrsqrt, 8 vdiv, 7 vsqrt) | 42 | 0 | 0 |
| submain.bin | 5 | 0 | | | |
| demo, game, single, netwk, nethttp, netaq | 0 | 0 | | | |
| netdnas.bin | 104 (see note) | 0 | | | |

Distance from producer to VWAITQ: 1 instruction (35 cases), 2 (3), 4 (2), 5 (1), 12 (1).

Backward, from each of the 46 reads of Q in the main ELF, to the nearest VWAITQ, producer or
function start: **45 have a VWAITQ before them**. The remaining one is a `cfc2` of Q at
0x102144. Its function (0x102074-0x1021dc) stores all 32 VF registers and reads every VI and
control register once: a VU0 register dump. Inferred from its contents; it sits in the Sony
library range (0x100000-0x11DFFF, decomp ROADMAP) and isn't named in the decomp yet. A dump
copies Q; it doesn't use a division result.

## Other things the scan showed

- **The gameplay overlay has no VU0 code.** GAME.BIN, DEMO, SINGLE and the network overlays
  contain no COP2 instructions. VU0 maths lives in the main ELF (`vu0.h`'s helpers), and
  SUBMAIN uses 5 ops.
- **One VU0 microprogram call**: a `vcallmsr $vi27` at 0x102064, next to the register dump.
  This partly answers M4's question "does the game use VU0 microprograms?": the main ELF calls
  one, from what looks like library code. What it runs is not known yet.
- **NETDNAS.BIN is mostly undecodable** (2,887 invalid words). That fits the decomp's description
  of it as obfuscated DNAS code; its 104 "VU0 ops" are almost certainly data decoded as code.

## Limits of this result

- Static analysis: it shows what the code can do, not what runs. A read reached only through
  a computed jump into the middle of a function wouldn't be followed. The backward pass makes
  this unlikely (every Q read has its VWAITQ in the same straight-line stretch), but it's not
  proof.
- The backward pass walks straight back. It doesn't follow branches into the read.
- 4 of the 9 binaries are English-patched. The decomp measured the patch as text data plus one
  instruction per game (TRANSLATION.md), so it's unlikely to touch VU0 code; the original
  binaries weren't scanned.
- Still **unknown**: whether the EE stalls on its own when macro-mode code reads Q early. With
  no early reads in Outbreak, that question doesn't affect this game.
